# ADR 0001: Retention of Vite + React 19 Editorial Frontend and Deferral of Next.js Migration

* **Status**: Accepted
* **Date**: 2025-03-30
* **Deciders**: Kārigar Engineering Architecture Board

## Context and Problem Statement

The Kārigar marketplace frontend is currently built using React 19, Vite 7, and Tailwind CSS v4. It features complex, scroll-linked editorial animations, interactive hero transformations (`useScrollProgress`), custom cursor tracking, and instant hash-based route overlays (`#object/[id]`).

As the project prepares for production backend integration, an architectural evaluation is required: Should the frontend immediately migrate to Next.js App Router, or remain a client-side Vite Single-Page Application (SPA) communicating with a separate backend API?

## Decision Drivers

1. **Editorial Animation Performance**: The hero section, craft atlas, and story sections rely heavily on client-side scroll measurement, CSS transforms, and frame synchronization.
2. **Developer Velocity & Solo-Developer Scope**: Migrating to Next.js App Router requires rewriting client state, layout boundaries, and route transitions, adding risk without immediate transactional benefit.
3. **Server/Client Boundary Hygiene**: The existing codebase strictly isolates client browser APIs (`window.location.hash`, `localStorage`) into hooks (`useHashRoute`, `useScrollProgress`) while maintaining side-effect-free domain types and static records.
4. **Decoupled Architecture**: Keeping frontend and backend strictly decoupled via HTTP/JSON API contracts allows independent scaling and simplifies deployment.

## Considered Options

1. **Option A (Accepted)**: Maintain Vite + React 19 frontend as a separate SPA deployed to CDN/Edge, connecting to a Node.js/TypeScript backend API.
2. **Option B (Rejected)**: Immediate migration to Next.js App Router.

## Decision Outcome

**Chosen Option**: Option A — Retain Vite + React 19 for the frontend application.

### Positive Consequences

* **Animation Safety**: Zero risk of destabilizing scroll-linked transitions or client-side DOM interactions.
* **Separation of Concerns**: Clean HTTP/JSON API boundary between presentation and domain services.
* **Build & Test Speed**: Vite provides sub-second HMR and deterministic production bundle generation via `vite build`.
* **Deployment Simplicity**: Frontend static artifacts build directly to static storage / CDN (e.g., Cloudflare Pages / Vercel Static), while backend runs in a Node/Bun container environment.

### Negative Consequences & Mitigation

* **SEO for Product Sheets**: Public product pages (`/object/[id]`) will rely on client-side rendering or edge pre-rendering/OG-tag generation for search indexing until SSR is introduced.
  * *Mitigation*: Public catalogue index endpoints are lightweight. Dynamic SSR/OpenGraph tags for shared social links can be generated by an Edge router proxy (e.g. Cloudflare Worker) without rewriting the main SPA.

## Codebase Invariants & Rules

1. All domain schemas in `src/types/` MUST remain client-agnostic and free of DOM or Vite-specific dependencies.
2. Route helpers in `src/lib/routes.ts` maintain URL format compatibility so that path-based routing (`/object/:id`) can be mapped cleanly when the backend API is introduced.
